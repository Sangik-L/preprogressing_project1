# 합성데이터 생성 계획

## 1. 목적과 생성 방식

이번 단계에서는 기존 SMT 센서 데이터의 분포와 5초 시퀀스 구조를 바탕으로 **15,132개 샘플의 반합성 센서 데이터**와 이에 연결되는 **합성 한국어 작업일지**를 만든다.

센서 데이터는 원본 시퀀스를 그대로 복제하는 방식이 아니라, 원본에서 샘플을 겹치지 않게 추출한 뒤 작은 변동을 추가해 분포와 센서 간 관계를 보존한다. 작업일지는 템플릿과 규칙을 조합해 생성하며 실제 작업자가 작성한 기록이라고 표현하지 않는다.

생성 과정에서는 먼저 정상적인 구조를 메모리에서 만든 뒤 계획된 품질 문제를 주입한다. 정상 상태는 별도 파일로 저장하지 않으며, 오류 위치별 manifest도 만들지 않는다. 최종적으로 전처리 대상인 센서 파일과 작업일지 파일만 저장한다.

## 2. 확정 규모

| 구분 | 규모 | 비고 |
|---|---:|---|
| 기본 센서 샘플 | 15,132개 | 샘플당 5개 측정행 |
| 기본 센서 측정행 | 75,660행 | 중복 오류 주입 전 기준 |
| 학습 | 12,106개 | 원래 Training에서 추출 |
| 검증 | 1,513개 | 원래 Training에서 추출 |
| 테스트 | 1,513개 | 원래 Validation에서 추출 |
| 작업일지 | 약 900~1,300건 | 실제 생성된 설비·교대·로트 조합에 따라 결정 |

15,132개는 10으로 나누어떨어지지 않으므로 정확한 정수 8:1:1은 만들 수 없다. 가장 가까운 정수 배분인 12,106:1,513:1,513을 사용하며 실제 비율은 약 80.003%:9.999%:9.999%이다.

전체 샘플 수 15,132개는 **중복 오류를 넣기 전의 정상적인 생산 샘플 수**를 뜻한다. 전체 샘플 중복과 측정행 중복을 주입한 뒤에는 전처리 전 데이터의 행 수가 이보다 증가한다.

### 3.3 식별자 최소화 판단

| 항목 | 이번 과제 판단 | 이유 |
|---|---|---|
| `sample_id` | 필수 | 센서 측정 5행을 하나의 샘플로 묶고 중복 샘플을 찾는 기준 |
| `log_id` | 필수 | 작업일지 한 건을 구분하고 로그 중복을 찾는 기준 |
| `equipment_id` | 필수 | 센서와 작업일지를 같은 설비 기준으로 연결하는 핵심 키 |
| `lot_id` | 유지 권장 | 동일 생산 묶음의 센서와 일지를 연결하고 분할 간 누수를 막는 그룹 키 |
| `sequence_no` | 유지 권장 | 5초 시퀀스 순서를 명확히 하고 중복 측정행을 진단하는 보조 키 |
| `shift_date`, `shift_code` | 유지 권장 | 교대 작업일지를 만들고 교대별 분포를 비교하는 범주 정보 |
| `line_id` | 제외 | `equipment_id`가 전체 데이터에서 고유하면 통합에 중복되는 계층 정보 |
| `work_order_id` | 제외 | 이번 데이터에서는 `lot_id`와 역할이 겹치며 생산계획 분석을 수행하지 않음 |
| `shift_id` | 제외 | `shift_date`와 `shift_code`의 조합으로 같은 정보를 표현할 수 있음 |
| `source_group_code` | 최종 파일에서 제외 | 원본 A~D 코드의 의미가 확인되지 않아 실제 공정 식별자로 해석할 수 없음 |

`split`과 `source_type`은 식별자가 아니라 데이터 관리용 메타데이터다. 원본 A~D 코드는 층화 추출 과정에서만 내부적으로 사용하고 최종 합성 파일에는 넣지 않는다.

실제 제조 시스템에도 설비, 자재 로트, 작업지시, 생산라인·작업장 같은 개념이 존재한다. ISA-95 기반 OPC UA 모델은 `EquipmentID`, `MaterialLotID`, `JobOrderID`를 정의하며 설비 계층에 생산라인, 작업장, 작업 단위를 둔다. SAP Digital Manufacturing도 작업장, 자원, 생산오더, 배치 번호를 사용한다. 다만 회사와 MES 제품마다 실제 컬럼명은 `설비코드`, `호기`, `RESOURCE`, `LOT_NO`, `BATCH`, `근무조`처럼 달라질 수 있다. 따라서 이번 프로젝트의 snake_case 이름은 국제적으로 고정된 실제 필드명이 아니라, 실제 공정 개념을 이해하기 쉽게 표현한 프로젝트용 스키마다.

| 프로젝트 컬럼 | 실제 공정·MES의 유사 항목 | 현장에서의 용도 | 실제성 판단 |
|---|---|---|---|
| `sample_id` | PCB·패널 ID, 일련번호, SFC, 검사 ID | 제품·검사·센서 묶음을 개별 추적 | 개념은 일반적이나 명칭은 공정마다 다름 |
| `log_id` | 일지번호, 이벤트 ID, 알림·정비 기록번호 | 작업일지 한 건을 수정·조회·중복 방지 | 시스템 내부 키로 일반적이며 작업자 화면에 안 보일 수 있음 |
| `equipment_id` | 설비코드, 호기, Equipment ID, Resource ID | 어느 설비에서 생산·측정·점검했는지 추적 | 실제 MES에서 매우 일반적 |
| `lot_id` | LOT_NO, Material Lot ID, Batch Number | 같은 자재·생산 묶음의 이력과 품질 추적 | 실제 제조 추적에서 일반적 |
| `sequence_no` | 측정순번, 이벤트 순번, 시퀀스 번호 | 같은 샘플 안의 센서 측정 순서 보존 | 공정 업무 라벨보다는 데이터 수집 시스템의 기술 컬럼에 가까움 |
| `shift_date` | 생산일자, 작업일자 | 자정을 넘는 야간조를 같은 작업일로 집계 | 교대제 공장에서 흔하지만 회사별 기준이 다름 |
| `shift_code` | 근무조, 교대조, SHIFT, A/B/C조 | 조별 생산실적·이상·인수인계 집계 | 교대 운영 공장에서 일반적이지만 필수 표준 필드는 아님 |
| `split` | 해당 없음 | 머신러닝 학습·검증·테스트 구분 | 실제 공정 컬럼이 아닌 프로젝트 전용 메타데이터 |
| `source_type` | 데이터 출처·수집방식 메타데이터 | 합성 데이터임을 표시 | 생산 공정 필드라기보다 연구 데이터 관리용 |

즉, `equipment_id`와 `lot_id`는 실제 공정 데이터와 가장 직접적으로 대응한다. `sample_id`와 `log_id`도 실제 시스템에 필요한 고유키 개념이지만 현장 명칭은 다양하다. `sequence_no`, `shift_date`, `shift_code`는 분석과 작업일지 구조를 위해 현실적인 보조 컬럼이다. `split`과 `source_type`은 실제 MES 데이터를 흉내 내기 위한 값이 아니라 과제의 재현성과 정직한 출처 표시를 위한 값이다.

## 4. 생성 순서

### 1단계. 원본 인덱스 구성

1. ZIP 파일을 직접 읽어 XLSX와 JSON의 대응 목록을 만든다.
2. 파일명에서 원래 제공 분할, 정상·불량, 결함 유형, A~D 코드와 시각을 읽는다.
3. XLSX의 5개 측정행과 JSON 라벨이 일치하는지 확인한다.

완료 기준:

- 원천 XLSX와 라벨 JSON이 27,830건 모두 일대일 대응한다.
- 샘플마다 센서 측정행이 5개이고 필수 센서 컬럼이 존재한다.
- 원본 파일은 읽기만 하고 압축 해제본이나 수정본을 만들지 않는다.

### 2단계. 15,132개 기준 샘플 선정과 분할

1. 기존 Training에서 13,619개를 `정상·불량 × 결함 유형 × A~D 원본 코드` 비율을 고려해 층화 추출한다.
2. 이 중 12,106개를 학습, 1,513개를 검증 데이터로 배정한다.
3. 기존 Validation에서는 같은 층화 기준으로 1,513개를 추출해 테스트 데이터로 사용한다.
4. 하나의 원본 시퀀스는 한 분할에서만 사용한다.

완료 기준:

- 학습·검증·테스트 사이에 원본 파일 stem이 겹치지 않는다.
- 전체 및 분할별 정상·불량과 결함 유형 비율이 원본에서 크게 벗어나지 않는다.
- 랜덤 시드를 고정해 같은 표본을 다시 만들 수 있다.

### 3단계. 센서 시퀀스 반합성

1. 샘플의 5개 측정행을 하나의 시퀀스로 유지한다.
2. 센서별 변동 크기는 학습 데이터에서 계산한다.
3. 시퀀스 전체의 수준을 조금 이동시키는 오프셋과 측정행별 작은 잡음을 함께 적용한다.
4. 잡음은 센서별 학습 표준편차의 작은 비율로 제한하고 원본의 물리적 범위를 심하게 벗어나지 않도록 자른다.
5. 원래 정상·불량 및 결함 유형 라벨은 변경하지 않는다.

초기 권장값은 시퀀스 오프셋을 학습 표준편차의 3% 이내, 행별 잡음을 1% 이내로 두는 것이다. 최종 값은 생성 후 분포 검증 결과에 따라 한 번만 조정한다.

완료 기준:

- 오류 주입 전 모든 샘플이 5행 구조와 시간 순서를 유지한다.
- 센서별 평균·중앙값·표준편차와 주요 분위수가 원본과 유사하다.
- 센서 간 상관관계와 5초 내 변화량의 형태가 원본과 유사하다.

### 4단계. 합성 운영 식별자 생성

1. 원본 A~D 코드는 표본 분포 유지에만 사용하고 실제 설비나 라인으로 해석하지 않는다.
2. 별도의 합성 `equipment_id`를 결정적으로 배정한다.
3. 하루를 주간·야간 2교대로 나눠 `shift_date`와 `shift_code`를 만든다.
4. 같은 설비에서 시간상 인접한 샘플을 20~40개씩 묶어 `lot_id`를 만든다.
5. 모든 운영 식별자는 분할 안에서만 생성해 로트나 작업일지가 분할을 넘지 않게 한다.

완료 기준:

- 하나의 `lot_id`가 여러 분할에 동시에 나타나지 않는다.
- 모든 센서 샘플에 설비·로트·교대 정보가 배정된다.
- 동일 설비의 시간 순서와 로트 구간이 모순되지 않는다.

### 5단계. 합성 작업일지 생성

작업일지는 센서 샘플마다 한 건씩 만들지 않고 다음 단위로 만든다.

1. **교대 로그**: 실제 샘플이 존재하는 `설비 × 날짜 × 교대`마다 시작점검 또는 인수인계 기록을 만든다.
2. **생산실적 로그**: 로트가 끝날 때 한 건을 만든다.
3. **이벤트 로그**: 학습 데이터에서 정한 강건한 센서 변화 기준으로 경고·점검·조정 사건을 만들되, 정상·불량 라벨과 결함 유형은 사용하지 않는다.
4. 문장은 현상, 조치, 재가동 여부, 추이 관찰을 조합한 짧은 한국어 기록으로 생성한다.
5. 작업 중 `operation` 일지는 당시 관찰 가능한 현상과 조치만 기록한다.
6. 검사 후 `post_inspection` 품질일지에는 `정상`, `불량`과 최종 결함명을 포함할 수 있다.

작업일지 수는 고정 숫자를 억지로 맞추지 않고 실제 생성된 설비·교대·로트 수에 따라 약 900~1,300건이 되도록 설계한다.

완료 기준:

- `operation` 일지에는 정상·불량 라벨이나 세부 결함명이 없다.
- `post_inspection` 일지는 검사 완료 뒤의 판정 기록임이 구분된다.
- 각 일지는 센서 데이터의 시간·설비·로트 중 하나 이상의 근거와 연결된다.
- 동일한 최종 문장이 서로 다른 분할에 완전히 똑같이 반복되지 않는다.
- `log_type`별 문장 수와 문장 길이 분포를 확인할 수 있다.

### 6단계. 계획된 품질 문제 주입

정상 구조는 파일로 저장하지 않고 메모리에서 바로 다음 문제를 넣는다.

| 대상 | 품질 문제 | 적용 계획 |
|---|---|---:|
| 센서 | 센서값 결측 | 기본 샘플의 3%, 샘플당 1~2개 센서 셀 |
| 센서 | 스파이크·이상치 | 기본 샘플의 1%, 샘플당 1개 센서값을 원칙으로 함 |
| 센서 | 전체 샘플 중복 | 기본 샘플의 0.5%, 새 `sample_id`를 가진 중복 복사본 추가 |
| 센서 | 샘플 내부 측정행 중복 | 기본 샘플의 1%, 선택한 측정행 1개 추가 |
| 작업일지 | 결측 | 기대되는 연결 또는 텍스트의 5% |
| 작업일지 | 중복 | 로그의 2%, 완전 중복과 내용 중복으로 나누어 적용 |
| 작업일지 | 약어 | 비결측 로그의 15% |
| 작업일지 | 불규칙한 띄어쓰기 | 비결측 로그의 7% |
| 작업일지 | 오탈자 | 비결측 로그의 3% |
| 작업일지 | 설비명 표기 차이 | 비결측 로그의 5% |
| 연결 | 시각 불일치 | 연결된 기본 샘플의 0.5% |
| 연결 | 설비 불일치 | 연결된 기본 샘플의 0.5% |

추가 규칙:

- 센서 오류와 텍스트 오류는 학습·검증·테스트에 같은 비율로 각각 주입한다.
- 오류 대상 선택에는 정상·불량 라벨과 결함 유형을 사용하지 않는다.
- 결측 작업일지와 연결 불일치가 같은 대상에 겹치지 않게 한다.
- 텍스트 오류는 로그 한 건에 최대 두 종류까지만 겹치게 한다.
- 실제 생성 건수는 `docs/합성데이터_오류설계.md`에 기록한다.

### 7단계. 생성 결과 검증과 저장

파일 저장 전 다음 항목을 자동 검사한다.

1. 기본 샘플 수와 분할별 샘플 수
2. 오류 주입 전 5행 시퀀스 구조와 시간 순서
3. 중복 주입 후 증가한 샘플 수와 측정행 수
4. 센서별 자료형, 결측률, 이상치 후보 수
5. 작업일지 유형별 건수, 빈 텍스트 수, 완전·내용 중복 수
6. 약어·띄어쓰기·오탈자·설비명 변형의 실제 건수
7. 정상적인 연결률과 계획적으로 만든 시간·설비 불일치 건수
8. 정답 표현과 12개 결함명이 `operation` 일지에는 없고 `post_inspection` 일지에만 있는지 여부
9. 분할 사이 `sample_id`, `lot_id`, `log_id` 중복 여부
10. 원본과 반합성 센서의 분포 및 상관관계 차이

검증을 통과한 경우에만 두 Parquet 파일을 저장한다. 별도의 행 단위 정답 파일이나 오류 위치 manifest는 저장하지 않는다.

## 5. 분포 유사성 판단 기준

다음 기준은 합성 데이터를 처음 생성할 때 적용할 실무적인 허용 범위다.

| 비교 항목 | 초기 허용 기준 |
|---|---|
| 정상·불량 비율 | 원본 대비 차이 0.5%p 이내 |
| 결함 유형 비율 | 원본 대비 차이 0.5%p 이내를 목표로 함 |
| 센서 평균 | 원본 표준편차 기준 표준화 평균 차이 절댓값 0.1 이하 |
| 센서 표준편차 | 원본 대비 비율 0.9~1.1 |
| 센서 간 상관계수 | 주요 쌍의 절대 차이 0.1 이하 |
| 5초 내 변화량 | 원본과 반합성 데이터의 중앙값·사분위범위 비교 |

수치 기준만으로 통과 여부를 정하지 않고 히스토그램, 상자그림, 센서 시퀀스 예시도 함께 확인한다. 분포가 지나치게 달라지면 잡음 크기만 조정하며, 목표 비율을 맞추기 위해 라벨을 변경하지 않는다.

## 6. 구현 파일 계획

생성 코드는 가능한 한 하나의 실행 파일로 구성한다.

- `scripts/01_generate_synthetic_data.py`: 원본 읽기, 표본 선정, 센서 반합성, 운영 식별자 및 작업일지 생성, 오류 주입, 검증, 저장
- `docs/합성데이터_오류설계.md`: 계획 비율과 실제 생성 건수 기록
- `outputs/synthetic_generation/`: 원본과 반합성 데이터의 분포 검증표 및 그래프

권장 랜덤 시드는 `42`이며, 표본 추출·센서 잡음·작업일지 생성·오류 주입은 같은 시드에서 파생한 별도 난수 생성기를 사용한다.

## 7. 실행 순서와 중단 지점

1. 원본 스키마와 라벨 대응 검사
2. 15,132개 표본과 8:1:1 분할 확정
3. 센서 반합성 및 분포 검증
4. 운영 식별자와 작업일지 생성
5. 누수 표현과 연결 구조 검증
6. 품질 문제 주입
7. 최종 자동 검사와 파일 저장
8. 실제 오류 건수 및 분포 결과 문서화

3단계의 센서 분포 검증에 실패하면 작업일지와 오류를 만들기 전에 중단한다. 5단계에서 정답 표현이나 분할 간 그룹 중복이 발견되어도 오류 주입 전 중단한다. 이 중단 지점을 두어 잘못된 데이터를 끝까지 생성하는 일을 막는다.

## 8. 완료 기준

다음을 모두 만족하면 합성데이터 생성 단계를 완료한 것으로 본다.

- 반합성 센서 데이터와 합성 작업일지 파일이 각각 생성되었다.
- 기본 센서 샘플 15,132개의 분할과 라벨 분포가 계획과 일치한다.
- 원본과 반합성 센서의 주요 통계, 분포, 상관관계와 시퀀스 형태가 유사하다.
- 작업 중 일지는 정답을 노출하지 않고, 검사 후 품질일지는 `record_stage`로 명확히 구분된다.
- 이후 모델 입력용 전처리에서는 `post_inspection` 일지를 제거한다.
- 정해진 품질 문제가 계획한 수준으로 포함되었다.
- 실제 오류 건수와 생성 조건이 문서에 기록되었다.
- 같은 랜덤 시드와 실행 코드로 결과를 다시 생성할 수 있다.
